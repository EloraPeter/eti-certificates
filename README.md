# eti-certificates

Independent certificate issuance, instructor/admin workflow, and
public verification for Elora Tech Institute. Shares the **same
Supabase project/database** as `ETI-cohort`, but is a separate repo,
separate codebase, and separate deployment. See
`supabase/migrations/001_certificate_schema.sql` for the exact
dependency this repo has on `ETI-cohort`'s existing schema.

This repo does **not** modify `ETI-cohort` in any way — no shared
files, no shared components, no HTTP dependency between the two apps.
See "Authentication" below for the one place this needed real
investigation rather than assumption.

## Authentication — cross-app session reuse

Per the directive, before building `/admin` and `/instructor/login` I
checked whether a session created by signing into `ETI-cohort` could
be reused seamlessly by this separate app/deployment (true SSO)
rather than requiring a second sign-in.

**Finding:** `ETI-cohort`'s client-side auth (`AdminAuthContext`,
`verifyAdminRequest`, `verifyInstructorRequest`, as inspected during
reconnaissance) uses Supabase Auth's default browser session,
obtained via `supabase.auth.getSession()` and sent as a bearer token
on API calls. There is no middleware, and no evidence of Supabase
Auth being configured with shared-domain cookies (which is the
mechanism that *would* enable real cross-subdomain SSO — e.g. a
session cookie scoped to `.eloratechinstitute.com` rather than to one
specific subdomain). By default, `@supabase/ssr`'s browser client
persists the session in `localStorage`, which is strictly
origin-scoped by the browser itself — a session created on
`ETI-cohort`'s domain is simply not visible to JavaScript running on
this app's domain, regardless of anything either app's code does.

**Conclusion:** true SSO is not currently possible without changing
`ETI-cohort`'s own cookie/session configuration (setting a shared
parent-domain cookie) — and the directive is explicit that
`ETI-cohort`'s authentication should not be modified "unless
explicitly instructed." It wasn't, here. So, per the directive's own
fallback instruction, this repo implements a **thin login** using the
same Supabase Auth project and credentials — `app/admin/page.tsx` and
`app/instructor/login/page.tsx` are plain
`supabase.auth.signInWithPassword()` forms against the same project.
No new account system, no duplicate users, no duplicate passwords —
an admin or instructor who can sign into `ETI-cohort` can sign into
this app with the exact same email/password, they just have to do it
once per app/domain.

If real SSO becomes worth building later, the concrete next step
would be a conversation with whoever owns `ETI-cohort`'s auth
configuration about switching to a shared-domain cookie strategy —
not something to retrofit unilaterally from this side.

### Why `ADMIN_EMAILS` instead of `NEXT_PUBLIC_ADMIN_EMAILS`

`ETI-cohort` uses `NEXT_PUBLIC_ADMIN_EMAILS` (a client-visible
variable — presumably because its client-side context wants to make
a UX decision, like showing/hiding a nav item, without a round trip).
This repo deliberately uses a **server-only** `ADMIN_EMAILS` instead,
per the directive's explicit instruction (§14/§23). This is a genuine
divergence from `ETI-cohort`'s own convention, made because the
directive asked for it plainly — not a claim that `ETI-cohort`'s
choice was wrong for its own purposes. `ETI-cohort`'s variable is
untouched.

## Database dependency

This repo's migrations (`supabase/migrations/001` and `002`) assume
the following already exist in the shared database, created by
`ETI-cohort`'s own migrations:

- extension `pgcrypto`
- function `set_updated_at()`
- tables `cohorts`, `students`, `instructors`, `instructor_cohorts`,
  `curricula` (columns as inspected during reconnaissance — see
  the architecture plan doc for the full column list read directly
  from `ETI-cohort`'s migration files 001, 002, 003, 009, 010, 011)

This repo's migrations do not create, alter, or drop any of those
tables. They only reference `students(id)`, `cohorts(id)`,
`instructors(id)`, and `curricula(id)` via foreign key.

## Certificate number vs. verification token

Two separate identifiers, generated by two separate mechanisms, on
purpose (directive §5/§6/§26):

| | Certificate number | Verification token |
|---|---|---|
| Example | `ETI-CERT-2026-00001` | `8f4c9e2a7b13d6f4c8a91e0b3d7f2c66` |
| Purpose | Human-readable identifier, printed on the certificate | The only credential the public verification endpoint accepts |
| Generation | Year-scoped counter (`certificate_number_counters` table + `allocate_certificate_number()`), reset to 00001 each new year | `encode(gen_random_bytes(16), 'hex')` — pgcrypto CSPRNG, 16 random bytes |
| Guessable? | Yes, by design (sequential) — this is fine because it is never used for lookup | No — this is the entire point |
| Public API lookup key | Never | Always (`GET /api/verify/[token]`) |

The year-scoped counter is implemented as an atomic
`INSERT ... ON CONFLICT DO UPDATE ... RETURNING` upsert on a
one-row-per-year table, which Postgres serializes at the row level —
concurrent issuance calls in the same year cannot receive duplicate
sequence numbers without needing an explicit `SELECT ... FOR UPDATE`.
See the extended comment in `001_certificate_schema.sql`.

## Workflow state machine

```
pending_instructor → pending_admin → approved → issuing → issued
        ↓                  ↓
    rejected            rejected

(cancelled reachable from pending_instructor or pending_admin)
admin override: pending_instructor → pending_admin (mandatory notes)
```

Enforced in `lib/certificates/workflow.ts` via an explicit
allow-list map (`assertTransition`), called by every route that
changes `status`. This is what makes the directive's list of
forbidden transitions (`issued → approved`, `rejected → approved`,
etc.) structurally unreachable rather than just discouraged — there
is no entry in the map that permits them, so calling
`assertTransition` for any of them throws before any database write
happens.

Certificate revocation is a **separate**, certificate-level status
change (`certificates.status: issued → revoked`), not a
`certification_requests` transition — see `app/api/admin/certificates/[id]/revoke/route.ts`.
There is no un-revoke path in v1.

## Issuance — idempotency and recoverability

PostgreSQL and Supabase Storage cannot share one atomic transaction —
a storage upload can succeed after a DB write fails, or vice versa.
`lib/certificates/issue.ts` is designed around that reality rather
than pretending otherwise:

1. Idempotency check first, before any mutation: if a `certificates`
   row already exists for this request **and** has a `pdf_path`, it's
   already fully issued — return it, do nothing else.
2. If a `certificates` row exists but `pdf_path` is null (a previous
   attempt died between insert and upload), resume from PDF
   generation using that same row — never insert a second one. The
   DB's `UNIQUE` constraint on `certification_request_id` is a second
   line of defense against this even under a race between two
   concurrent calls.
3. `approved → issuing` happens before any storage work begins, so a
   request that's mid-issuance is visibly distinguishable from one
   that's simply approved-and-not-yet-attempted.
4. On any failure, the request is left at `issuing` (not reverted) —
   an `issuance_failed` audit event is logged, and the error is
   returned to the caller. The admin UI's "Issue certificate" button
   can simply be clicked again; that's the retry mechanism.

## Audit trail

`certificate_audit_log` is append-only, enforced at the **database**
level: `BEFORE UPDATE` and `BEFORE DELETE` triggers reject any
mutation outright, including from the service-role connection itself
— not just "no application code does this," but "no code path can."
See `lib/certificates/audit.ts` for the closed set of `event_type`
values in use, and `logAuditEvent()` for the writer (deliberately
non-throwing on failure — an audit-write failure must never block the
underlying workflow action that already succeeded).

## Rate limiting

`lib/rateLimit/tokenBucket.ts` — a basic in-memory, per-IP token
bucket (30 requests/minute) applied to `GET /api/verify/[token]` and
`GET /api/verify/[token]/pdf`.

**Documented limitation:** this is an in-process `Map`, not shared
across serverless function instances. On a platform that scales this
route horizontally, each instance enforces its own independent limit
— the effective global ceiling is higher than the configured
per-instance number. This is an accepted, zero-cost, zero-dependency
tradeoff for v1, not a claim of complete abuse protection. If real
abuse is observed, or the deployment target is confirmed to run many
concurrent instances, the documented upgrade path is a shared store
(Upstash Redis is the natural fit for a Vercel deployment) behind the
exact same `isRateLimited()` function signature — no call-site
changes needed.

## Storage

`certificates` bucket is **private** (final decision per directive
§9 — supersedes the earlier planning doc, which had recommended
public). PDF access is always via a server-generated signed URL with
a 5-minute expiry (`lib/certificates/pdf/access.ts`). The public
verification page and API never return a raw storage path or a
permanent public URL — only a same-origin route
(`/api/verify/[token]/pdf`) that looks the certificate up by token
and redirects to a freshly generated signed URL.

## Service-role security

The service-role key grants full read/write access to the **entire**
shared Supabase project, not just the six certificate tables. This is
a named, accepted architectural boundary (directive §19), not
something the database enforces — nothing in Postgres stops this
app's key from writing to `students` or `payments`. The boundary is
**code discipline**: every file in this repo that touches a shared
table does so with `SELECT` only (visible by grep — search for
`.from("students")`, `.from("cohorts")`, `.from("instructors")`, none
of which are ever followed by `.insert(`, `.update(`, or `.delete(`
in this codebase). If a stronger, database-enforced guarantee is
wanted later, a dedicated Postgres role scoped to only the
`certificate_*` tables plus `SELECT` on the shared ones (used instead
of the full `service_role` key) is the concrete next step — noted as
a possible hardening, not implemented in v1.

## Creating a request from the UI

`/admin/requests/new` ("Nominate a student" button on the requests
page) lets an admin start a certification request from dropdowns —
cohort, then student and instructor scoped to that cohort (via the
read-only `/api/admin/cohorts/[id]/students` and `/instructors`
endpoints), then certificate type. It calls the same
`POST /api/certificates/request` endpoint a curl call would; the form
is UX, not a security boundary — the endpoint re-validates the
student's status and the instructor's cohort assignment itself
regardless of what the form offered.

## What was deliberately not built (v1 scope)

- **Student self-request.** The schema fully supports it
  (`certification_request_origin = 'student'`), but no UI or
  dedicated endpoint exists yet — `POST /api/certificates/request`
  only accepts an authenticated admin or instructor caller in v1, per
  directive §4 ("does NOT need to be implemented as a full v1 UI if
  it adds unnecessary complexity"). Adding it later means a new
  endpoint using `verifyStudentRequest` (ported the same way as
  `verifyAdmin`/`verifyInstructor`) and a form — no migration change.
- **True cross-domain SSO.** See "Authentication" above.
- **Certificate reissuance.** `certificate_reissued` exists as a
  reserved audit `event_type` but no code path emits it — a
  replacement credential, if ever needed, should be a new request/new
  certificate, not a mutation of a revoked one.
- **Email notification on issuance.** Not required by the directive;
  no Resend dependency was added.

## Local validation performed

No Node/npm toolchain is available in the sandbox this was built in
(network egress is disabled), so `npm install`, `next build`,
`tsc --noEmit`, and `next lint` were **not** run against this code —
that is real, meaningful validation this repo still needs before
first deploy, not a formality. What *was* checked manually while
writing:

- Every SQL statement in both migration files was hand-reviewed for
  syntax and for correct reference to `ETI-cohort`'s actual column
  names (not assumed ones — cross-checked against the full
  `CREATE TABLE` bodies read during reconnaissance).
  Migrations were **not executed** against any database, shared or
  otherwise — per the directive, that requires separate, explicit
  approval.
- Every `certification_requests.status` mutation in every route
  handler goes through `assertTransition()` — checked by grep, not
  just by design intent.
- Every file that imports `getAdminClient` or reads `SUPABASE_SERVICE_ROLE_KEY`
  has `import "server-only"` as its first import — checked by grep.
- No `NEXT_PUBLIC_*` variable references `ADMIN_EMAILS` or the
  service-role key anywhere in the codebase — checked by grep.
